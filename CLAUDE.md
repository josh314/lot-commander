# lot-commander

## Commands
- `npm run demon` — dev server via `nodemon`, delegated via `-w server` to `server/nodemon.json`; its `events` hook re-runs `npm run lint` on every start/restart
- `npm run dev-server-legacy` — `webpack-dev-server` for the legacy AngularJS client (renamed from `dev-server` when the client + build tooling moved to `client-legacy/`; see Modernize)
- `npm run lint-server` — delegates to `npm run lint -w server`; eslint against `server/src` using `server/.eslintrc.js`
- `npm run build-client-legacy` — production webpack build of the legacy client (renamed from `build-client`; also `build-client-dev-legacy` for the dev-mode build)
- `npm run depcruise` — runs `dependency-cruiser` repo-wide; also the workspace-boundary check (flags a dependency used in one workspace but declared in another's `package.json`)
- `npm run debug` — `node inspect` entry point
- No test suite exists — verify JS with `node -c <file>` (see Server Modules below)
- No client-side lint script exists either — `node -c` doesn't apply to `client-legacy/src/js/ng` (Angular DI + ES modules); verify legacy client changes with `npm run build-client-legacy` (full webpack build catches syntax/wiring errors)
- Unlike `client-legacy`, the new `client/` has real standalone scripts: `npm run lint -w client`, `npm run build -w client` (`tsc -b && vite build`), `npm run test -w client` (`vitest run`), `npm run typecheck -w client` (`tsc -b`), `npm run check -w client` (lint + typecheck + test) — `test` alone never runs `tsc`, so passing tests give zero signal about type-level correctness; use `check`/`typecheck` for that
- `sed` on this dev machine is GNU sed, not BSD, despite Darwin — use `sed -i 'script' file`, not the BSD/macOS `sed -i '' 'script' file` (the latter fails with a misleading "can't read \<script\>" error)

## Infrastructure
- Terraform lives in `terraform/` with two root modules: `bootstrap-ecr` and `bootstrap-pipeline-iam`, each with `environments/sandbox-autarch` and `environments/wazuezoom`
- This repo's `terraform/` only bootstraps ECR push IAM — the actual ECS Fargate deployment and the task role's runtime AWS permissions (S3, Step Functions, SSM scoping) live in the sibling repo `~/dev/ops/lot-commander-ecs-deploy`; check its `terraform/modules/ecs-fargate-service/main.tf` for AccessDenied-shaped issues
- The GitLab provider reads `GITLAB_TOKEN` from the environment — no TF variable needed
- ECR push IAM role uses GitLab OIDC (`sts:AssumeRoleWithWebIdentity`); trust policy conditions: `sub` (wildcard), `aud` (`sts.amazonaws.com`), `namespace_id`, `project_id`
- `server/src/load-config.js` loads config async at startup: if `server/config.local.json` exists it's used (SSM not contacted, gitignored, for local dev); otherwise config is pulled from SSM Parameter Store at `/lot-commander/<APP_ENV>/config` (`APP_ENV` required in that case)
- AI-backfill runtime config (`aiBackfill.jobsBucket`, `aiBackfill.aggregateStateMachineArn`) lives in the same SSM config blob — `jobsBucket` must be a bucket **name**, not an ARN
- `.gitignore`'s `config.*` pattern blanket-excludes any `config.*`-named file — new tracked config files (e.g. `server/config.example.json`) need an explicit `!` exception added
- Root `.npmrc` hardcodes a GitLab auth token for the `@wazue` scoped registry — required to install `@wazue/barcodes`, `@wazue/excel`, `@wazue/upc-item-db`; don't delete/replace this file casually
- `server/config.example.json` is the canonical documented config shape (sanitized, placeholder credentials) — template for both `server/config.local.json` (local dev) and the SSM parameter (deployed envs, via `set-ssm-env-config.js`); keep it in sync when adding new config keys
- Session secrets: SSM `SecureString` at `/lot-commander/<APP_ENV>/session-secrets` (comma-delimited list, first signs new cookies, all accepted — enables rotation); locally, `SESSION_SECRET` env var is used instead whenever `config.local.json` is present (`server/src/load-config.js`'s `isLocal()`), regardless of `APP_ENV` — both `load-config.js` and `app-session.js` must agree on this check, since they previously used different heuristics and could disagree

## CI/CD (`.gitlab-ci.yml`)
- `build` job is env-agnostic: tags image `app:$CI_COMMIT_SHORT_SHA`, saves as `image.tar.gz` artifact (3hr expiry)
- Push jobs retag from `app:$CI_COMMIT_SHORT_SHA` to ECR destination; they hold environment-specific vars
- `push-wazuezoom` auto-triggers on semver tags (`\d+\.\d+\.\d+$`); all other push jobs are manual with `allow_failure: true`
- Push jobs always tag/push `$CI_COMMIT_SHORT_SHA` and `latest`; `IMAGE_TAG` and `CI_COMMIT_TAG` are tagged/pushed independently if each is set (not a fallback of one to the other)
- `docker:29` image has no bash (Alpine, no `bash` package) — CI script lines must use POSIX `sh` syntax: `[ ]` not `[[ ]]`, no `-v` test operator
- apk `aws-cli` is broken on Alpine 3.20+ — install via `pip3` with `--break-system-packages`

## Runtime & Networking
- Production sits behind an AWS ALB; `server.js:listen()` does NOT set `keepAliveTimeout`/`headersTimeout` on the Node.js HTTP server — known gap (Node default 5s < ALB idle timeout 60s → intermittent 502s)
- `shopify-gql.js` uses bare `axios()` with no keep-alive HTTP agent; each Shopify API call opens a new TCP/TLS connection
- Two MongoDB connections at startup: main via `mongoose.createConnection()` in `server.js`, second via `connect-mongodb-session` in `app-session.js`
- Four separate `S3Client` instances, each with independent connection pools: `media-server.js`, `document-svc.js`, `manifest-svc.js`, `product-data.js`
- `bstock-db.js` creates its client at module load time using the `__mongooseConnection` global — must be required after `server.init()` completes
- `global.__config` (set in `Server` constructor, before `init()` runs) is read at module-load time by `media-server.js`, `manifest-svc.js`, `document-svc.js`, `product-data.js` for S3 bucket/CloudFront config — same load-order hazard as `bstock-db.js`'s `__mongooseConnection` use

## Server Modules (`server/src/modules/`)
- No automated test suite exists in this repo (no `*.test.js`/`*.spec.js` anywhere) — verify JS changes with `node -c <file>` and manual/code review, not a test run
- Existing caching pattern for external API lookups: `fnsku-to-asin.js` and `traject.js` each implement a Mongo-backed `Cache` class (separate collection, TTL checked against `updatedAt`) — persists across restarts. For caching data already backed by a local Mongo model (e.g. `app-settings.js`), prefer a simpler in-memory cache instead
- Modules are wired in `server.js`'s `init()` (lines 115-440, `Commander` instantiations at ~147-367) as `new XCommander(model, options)`, then bundled into a single dependency object passed to `routers/index.js`
- `product-data.js`'s `getProductDataByBarcode` only attempts a fetch-job-marker write (`createFetchJobIfLotNotLocked`, S3 key `fetch/<lotId>/<barcode>`) on the no-`source` lookup path — an explicit `source` is an intentional probe-only call with no fallback. The write silently no-ops (no log either way) if the Lot is already `Pending Data`
- Product-data source integrations (`upc-item-db.js`, `traject.js`) must return `null`/falsy on a miss, not a truthy placeholder — `getProductDataByBarcode`'s `if(product)` check decides whether fetch-job creation fires. `traject.js` intentionally swallows upstream API errors as a fallback-to-UpcItemDb design (logged via `console.warn`, not fully silent) so a transient upstream failure doesn't block scanning
- For an intentionally-empty S3 `PutObjectCommand` body (e.g. `product-data.js`'s fetch-job marker), use `Buffer.alloc(0)`, not `''` — `@smithy/middleware-content-length` only computes/sets `content-length` when `body` is truthy, and `''` is falsy in JS, so an empty string skips the header entirely and re-triggers the SDK's "stream of unknown length" warning it was meant to silence
- To reproduce/verify AWS SDK request-middleware behavior (e.g. that warning) without real credentials or network access: point `S3Client` at `endpoint: 'http://127.0.0.1:1'` with dummy credentials and `maxAttempts: 1`, then `.send()` and `.catch()` the resulting network error — middleware (incl. `console.warn`s) runs before the failed connection, so console output up to that point reflects real client behavior
- `getPublicInfo()`'s `id` field (`user-db.js:227`, Mongoose `this.id`) is a MongoDB ObjectId string (24 hex chars), not a UUID — a Zod schema validating it needs `z.string().min(1)`, not `.uuid()` (caught by a test failing with `ZodError: Invalid UUID`)

## Client (`client-legacy/src/js/ng/`)
- AngularJS 1.x + ui-router in `html5Mode` (pushState, no `#`); states and nav structure are centralized in `app.js`'s `stateData` array, not scattered per-feature
- `RootCtrl` (`root-ctrl.js`) is bound to `<html>` in `server/src/views/layouts/index.hbs` — it runs once per full page load, NOT per client-side state transition. Logic that must run on every navigation belongs in `app.js`'s `.run()` block (`$transitions.onBefore`/`.onSuccess`), not in `RootCtrl` or scattered across controllers
- Legacy ui-router events (`$stateChangeStart`/`$stateChangeSuccess` via `$rootScope.$on`) never fire in this app — they're a polyfill requiring an explicit dependency on the `ui.router.state.events` module, which `app.js`'s module list doesn't include. Use `$transitions.onBefore()`/`.onSuccess()` instead (core to `ui.router`, no extra module needed); redirect by `return`ing `$state.target(...)` from `onBefore`, not by calling `$state.go()` synchronously (gets silently swallowed mid-transition)
- Auth has two independent layers: the server session (Mongo-backed, 24h TTL, `app-session.js`) and a client-only daily-cutoff enforced by the `sessionTimeout` service (`session-timeout-svc.js`) via a `lotCommander` cookie, checked centrally in `app.js`'s `$transitions.onBefore` hook — they can desync (e.g. a stale un-cleared cookie forces a client logout right after a fresh server login)
- `auth.isLoggedIn` (`server.js`) wraps all routes under `/`, including `/api/*`, and does a bare `res.redirect('/login')` on failure — not XHR-aware, so a failed API call gets a redirect response rather than a 401 JSON body
- To test client-side cookie/timer logic without waiting (no client test suite exists): in the browser console, set the cookie directly (e.g. `document.cookie = 'lotCommander=' + encodeURIComponent(JSON.stringify({timeout: new Date(Date.now()-1000).toISOString()})) + '; path=/'`) and grab any Angular service via `angular.element(document.body).injector().get('serviceName')` to call its methods directly

## Client (`client/`)
- Tailwind is v4 via the `@tailwindcss/vite` plugin + a single `@import "tailwindcss";` in `index.css` — no `tailwind.config.js`/`postcss.config.js`; `eslint.config.js` uses `tseslint.configs.recommendedTypeChecked` (type-aware — needs `parserOptions.projectService: true` + `tsconfigRootDir: import.meta.dirname`) plus `@stylistic/eslint-plugin` for whitespace/style rules, since none of the "recommended" presets include those; `vite.config.ts`'s dev server binds port `9000` and proxies `/api`, `/login`, `/logout` to `http://localhost:8080` with `changeOrigin: true`
- `tsconfig.app.json`'s `types` must reference `@testing-library/jest-dom/vitest`, not the bare `@testing-library/jest-dom` — the latter augments Jest's `jest.Matchers` namespace, not Vitest's `Assertion` type, so matchers like `.toBeInTheDocument()` fail to typecheck even though they work fine at runtime (`vitest.setup.js` already imports the correct `/vitest` runtime entry)
- Because linting is type-aware (`recommendedTypeChecked`), a missing/wrong type declaration can surface as an unrelated-looking eslint error (e.g. `@typescript-eslint/no-unsafe-call`) instead of a `tsc` error — TS's error-recovery types an unresolved property as `any`, which type-aware eslint rules then flag; fixing the real type gap clears both at once
- `Array.prototype.filter` with a type-guard function (e.g. `route-config.tsx`'s `isNavGroup`) only narrows the result's type if the filter callback itself is annotated as a type predicate (`(x): x is T => ...`) — a plain boolean-returning callback leaves the array typed as the original union, and downstream use surfaces as `@typescript-eslint/no-unsafe-assignment` rather than a type error
- `npx tsc -b --dry` does NOT type-check anything — it only reports whether a build would run; for a real check use `npx tsc -b` (delete `node_modules/.tmp/*.tsbuildinfo` first to bypass the incremental cache) or `npx tsc --noEmit -p tsconfig.app.json`
- `npm run test -w client` (vitest, esbuild-based) does not fail on a broken type-only import (e.g. `import { type X } from './y'` where `y` no longer exports `X`) — esbuild strips type-only imports without resolving them, so only `npx tsc --noEmit -p tsconfig.app.json` catches it
- Zod schemas live in `client/src/schemas/` (e.g. `schemas/user.ts`'s `UserCookieSchema`/`UserCookie`, which replaced a hand-written interface in `lib/auth.ts`) — mirror `client/src/api/`'s per-resource grouping as response-validation schemas get added (e.g. `schemas/api/<resource>.ts`, one per file in `client/src/api/`), rather than one giant file
- Vite's dev-server `proxy` (`vite.config.ts`) is an explicit path allowlist, unlike `client-legacy/webpack.dev.js`'s `proxy: { '/': ... }` + `historyApiFallback` (which falls through to the backend for anything not served locally) — a plain `GET /` in the new client is served entirely by Vite and never reaches Express, so backend logic that used to run as a side effect of *any* request hitting `/` won't fire there; the `user` cookie is now set explicitly in the `POST /login` handler and cleared in `/logout`, not via generic request-path-keyed middleware
- Don't use the Cookie Store API (`window.cookieStore`) client-side — Chromium-only, unsupported in Firefox/Safari (and in jsdom); read cookies via a `document.cookie.match(/(?:^|; )NAME=([^;]*)/)` regex instead, as `client/src/lib/auth.ts` does
- React 19 context is provided via `<SomeContext value={x}>` directly, not `<SomeContext.Provider value={x}>` (see `client/src/components/AuthProvider.tsx`)
- axios (`client/src/api/api.ts`) rejects any non-2xx response by default — a response interceptor checking for the `auth.isLoggedIn` redirect-to-login-HTML case needs the check in *both* the fulfilled and rejected callbacks passed to `interceptors.response.use()`, or non-2xx responses skip it entirely
- `client/src/features/<domain>/` groups by nav-section/domain (matching `phase-3-screen-migration.md`'s screen groupings), not 1:1 per route/screen — e.g. `features/lots/` holds all `main.lots.*` screens, not just one component
- API calls are cut by backend resource, not by feature/domain — a resource (e.g. lots) is often consumed by multiple features, so its fetch/option-handling/response-parsing logic lives once in `client/src/api/<resource>.ts` (mirroring `server/routers/*.js`'s resource split), and `features/*` import from there rather than each owning duplicate API code. Legacy's `client-legacy/src/js/api.js` (~150 flat exported functions, one file for all resources) is the spiritual predecessor — same idea, just split per-resource instead of monolithic
- `getQueryString<T extends object>(obj: QueryParams<T>)` (`client/src/api/api.ts`) takes a homomorphic mapped type (`QueryParams<T> = { [K in keyof T]: QueryParamValue }`) so any resource's closed QP interface (e.g. `ListLotsQP`) can be passed without an index signature — `obj: object` is too loose (accepts non-primitives), and `obj: Record<string, QueryParamValue>` (or a same-shaped generic constraint) rejects named interfaces outright ("index signature missing"); making the QP interface itself `extends Record<string, QueryParamValue>` "fixes" that but silently drops exactness, letting typo'd extra keys through. This pattern is one-directional: `T` inferred through it only recovers keys/optionality, not original value types (they collapse to `unknown`), so it can't be reused to type a return value of type `T`
- Because of that `unknown`-collapse, `Object.entries()`/`Object.fromEntries()` on a `QueryParams<T>`-typed value types values as `unknown`, not `QueryParamValue` — building a `URLSearchParams`-compatible object needs an explicit `as Record<string, string>` cast at that point
- No Playwright/chromium-cli installed — verify new-client UI changes by driving headless Chrome directly via CDP (`Google Chrome.app/Contents/MacOS/Google Chrome --headless=new --remote-debugging-port=9222`, driven from Node via its native `WebSocket` global, Node 22+) against `npm run dev -w client`; fake auth by `Network.setCookie`-ing a `user` cookie shaped per `schemas/user.ts`'s `UserCookieSchema` (with a real `permissions` entry, e.g. `VIEW_LOT`) before navigating, since there's no backend/Mongo session to log in through
- `client/src/api/index.ts` re-exports each resource module as a namespace (`export * as lots from './lots'`) rather than attaching resources onto the shared axios instance (`api.lots = lots` doesn't type-check — `AxiosInstance` has no such property) or wrapping each resource in a class (unnecessary ceremony: the axios instance is a process-wide singleton, so a module-level closure over it already gives the same encapsulation constructor injection would)
- `client/src/api/api.ts`'s `createResourceClient(basePath)` scopes an `api/<resource>.ts` module's requests under a base path (e.g. `/lots`) while still routing through the shared `api` singleton, so the auth-redirect interceptor stays attached (a fresh `axios.create()` per resource would need interceptors re-registered manually) — since the singleton's `baseURL` is already `/api`, a resource's own `url`/`basePath` must NOT also start with `/api`, or axios concatenates both into a nonexistent path that falls through to the server's SPA catch-all (`res.render('main.hbs', ...)` in `server/src/routers/index.js`), returns HTML, and the auth interceptor misreads that as a logged-out session and redirects to `/login`
- `AuthProvider` (`client/src/components/AuthProvider.tsx`, wraps `<App/>` in `main.tsx`) owns the session via `useState` (lazy initializer reads the cookie at mount, not module-import time) and provides `{ user, refreshUser }` through `AuthContext`; the `/login` hard-redirect effect fires on no user *or* `userState.isDisabled`, and lives here too, not in `App.tsx`. `refreshUser()` re-reads the cookie and triggers a re-render but has no callers yet — reserved for `api/api.ts`'s content-type-check interceptor to call once that's wired to real `/api/*` calls (not dead code, just not yet connected)
- `getLoggedInUser(cookie: string)` (`client/src/lib/auth.ts`) is a pure function — it no longer reads `document.cookie` itself, callers pass the string in. `User`'s constructor takes an already-parsed `UserCookie` object, not a raw cookie string; all parsing (`decodeURIComponent`/`JSON.parse`/`UserCookieSchema.parse`) happens inside `getLoggedInUser`'s own `try/catch`, so a malformed cookie degrades to `undefined` there — if you ever move that parsing again, keep it inside the `try`, not before it, or a bad cookie throws uncaught during render instead of triggering the login redirect
- Because `getLoggedInUser` takes the cookie as a parameter, `AuthProvider` must call `document.cookie` fresh at each use site (inside the `useState` initializer, inside `refreshUser`'s callback body) rather than hoisting it into a render-scoped variable closed over by `useCallback` — a hoisted variable makes `refreshUser` replay a stale snapshot from whatever render created it, defeating its entire purpose (noticing a cookie that changed *after* the component last rendered)
- A context value that's an object literal (e.g. `AuthContext`'s `{ user, refreshUser }`) needs `useMemo` keyed on its fields, and any function inside it needs `useCallback` — otherwise every provider re-render creates a new object reference and re-renders every consumer even when nothing meaningful changed
- `useAuth()` (`client/src/hooks/auth.ts`) returns the raw `{user, refreshUser}`; `useAuthUser()` wraps it for the common case of only needing `.user` — used by `AppShell`, `Sidebar`, `RequirePermission`. `useAuth()` itself currently has no call sites outside `hooks/auth.ts` (intentional, see above)
- `client/src/lib/route-config.tsx`'s `RouteConfigNode` tree is the single source of truth for both routing and the navbar (mirrors legacy's `stateData` array, but tree-shaped to match React Router's `RouteObject` natively instead of ui-router's flat state registry) — `toRouteObjects()` derives the `createBrowserRouter` config, `buildNavItems()`/`filterNavEntries()` derive permission-filtered navbar data; each `features/<domain>/routes.ts` exports its own subtree, assembled centrally in `routes/index.ts`
- `routes/index.ts` assembles two separate `RouteConfigNode[]` trees — `navTree` (main scrollable nav) and `footerNavTree` (pinned-bottom nav, e.g. `/logout`) — spread together into one flat list for `toRouteObjects()`/routing, but walked independently by `client/src/components/Sidebar.tsx` for nav rendering; a node's tree membership *is* its placement, deliberately not a `nav.section`-style field, since a `nav.group` dropdown can only render in one place and a field would let the same group's members disagree on section with no compile-time signal
- `RouteConfigNode` is a discriminated union — `PrefixNode` (path-only grouping), `LayoutNode` (`layout` + `children`), `PageNode` (`IndexPageNode | NormalPageNode`, each wrapping `page`), `AnchorNode` (`nav.isAnchorTag: true`) — every field a variant doesn't own is typed `?: never`, so `layout`+`page` together, `index`+`children` together, or none of them, are compile errors, not runtime throws; `toRouteObject()`/`toRouteObjects()` have zero validation logic left. `AnchorNode` is still excluded from the route table entirely, same as before — walked by `buildNavItems()` for nav grouping but never routable client-side
- React Router's `_renderMatches` (confirmed in `node_modules/react-router/dist/development/lib/hooks.js`) renders a matched route's own `Component`/`element` if present, otherwise just passes through the next-deeper match untouched — nesting a node under `children` with no `layout` (a `PrefixNode`) changes nothing about what renders, it's purely a path-prefix/DRY device; only a real `LayoutNode` that places an `<Outlet/>` in its own JSX changes the render tree. Don't assume config-nesting implies a rendered layout
- `components/layout/Layout`'s `Component` field accepts any `ComponentType` — nothing enforces that it actually renders an `<Outlet/>`, and this isn't fixable at the type level (TS can't inspect a component's returned JSX for a specific descendant, only its prop/return shape). The real mitigation is a test, not a type — see `docs/modernization-todos/TODO.md` for the plan (a sweep test that discovers every `Layout` by walking the real route tree, rather than one hardcoded per component; blocked on `routes/index.ts` exporting its root `tree` and on a shared provider-wrapping render helper, since `AppShell` needs a real `AuthContext` user to get past its own early `return null`)
- `nav.group` is a closed union (`NavGroupLabel`/`NAV_GROUPS` in `route-config.tsx`), grown one entry at a time as each feature's dropdown is ported — a bare string would let a typo silently split or merge nav dropdowns across features with no compile-time signal
- `client/src/queries/<resource>.ts` is a layer between `api/<resource>.ts` and `features/`, wrapping `@tanstack/react-query` (added dep, plus `@tanstack/eslint-plugin-query`'s `flat/recommended-strict` in `eslint.config.js`; `App.tsx` wraps `RouterProvider` in one process-lifetime `QueryClientProvider`): each resource exports a `queryOptions()`-returning factory (e.g. `lots.ts`'s `listOptions()` — owns the query key, calls the `api/` fetch fn, hydrates the response into a `lib/` model class) plus a thin hook wrapper (`useList()` = `useQuery(listOptions())`) for component call sites — export both, not one or the other, since the options form stays usable outside components (router loaders, prefetch, `invalidateQueries` key-matching) while the hook is just the common-case convenience
- Domain model classes in `client/src/lib/` (e.g. `Lot`) only hydrate (constructor, server → model) and serialize (a `toPayload()`-style method, model → server payload) — unlike legacy's Angular service classes (e.g. `lot-svc.js`), they never perform the network call themselves; writes go through a `useMutation` in `queries/<resource>.ts` instead, so the mutation lifecycle (pending/error/success, cache invalidation) is owned by react-query, not the model
- TanStack Query's `placeholderData` (e.g. a static `[]` or `{count: 0}`) forces `status: 'success'` immediately, even before the first real fetch completes — a `queryOptions()` using it breaks a component's `if(isPending) return <Loading/>` check since `isPending` is false from the first render; use `keepPreviousData` instead (returns `undefined` when there's no prior data, so `isPending` stays true on first load, only supplying stale data on later param changes to avoid flicker)
- A `features/<domain>/routes.ts` route array needs an explicit `RouteConfigNode[]` annotation on export — without it, TS infers/widens literal fields (e.g. `nav.group` to plain `string`, `index: true` to `boolean`) before any union-member matching happens; the `index: true` case is the sharper failure since it then fails *every* `RouteConfigNode` member ("`boolean` not assignable to `true`") instead of just losing a narrower type silently. Prefer the plain array annotation over per-node `as`/`satisfies` — `as` only needs one-directional assignability and can admit shapes a real annotation would reject; `satisfies` is safe but only worth it for per-node intent signaling
- Legacy's `userPermission` (`client-legacy/src/js/ng/controllers/navbar-ctrl.js`) only ever filtered navbar links, never enforced route access — the new client's `RequirePermission` (`client/src/components/RequirePermission.tsx`), wrapped around a node's resolved component by `toRouteObject()` when the node has a `permission`, closes that gap by redirecting home if `user.isPermitted()` fails
- A `features/<domain>/routes.ts` node's `permission` must match what the server's `auth.isAuthorized(...)` actually requires for the endpoint(s) the screen calls, not just a semantically-similar permission — e.g. `server/src/routers/lots.js`'s list/count endpoints require `LIST_LOTS`, not `VIEW_LOT`, and `server/src/modules/user-db.js`'s `__USER_ROLE_PERMISSIONS__` grants some role groups (e.g. `__FULFILLMENT__`) one without the other, so a wrong guess silently lets a user reach a page whose queries then 403
- React Router route paths support optional segments via a trailing `?` on any segment, including mid-path (e.g. `path: 'pallets/:palletId?/split'`) — the eventual replacement for legacy's `optionalParams`/`squash` state config (see `main.inventory-pallets.split`/`.repack` in `client-legacy/src/js/ng/app.js`) once those screens are ported
- `@ts-expect-error` only suppresses a diagnostic reported on the *exact* next line — for a multi-line object literal, an error on a property a few lines into the literal won't be suppressed by a comment above the opening `{`, and since `tsconfig.app.json` sets `noUnusedLocals: true`, an unused binding on that same next line can silently consume the directive's "used" check instead, masking the real leaked error behind a false pass. Put the comment directly above the specific offending property, and `void` the binding if otherwise unused
- A `never`-padded discriminated union's invariants (e.g. `RouteConfigNode`'s mutual exclusivity) don't need a dedicated runtime test — `npm run test -w client` never runs `tsc`, so a `@ts-expect-error` assertion wrapped in `describe`/`test()` inside a normal `.test.tsx` file can never fail regardless of whether the invariant holds, which is worse than no test. Either rely on `npm run typecheck`/`npm run check` actually running before calling something done, or move the assertion to a `*.test-d.ts` file and run `vitest --typecheck` (default `typecheck.include: **/*.{test,spec}-d.ts`), which genuinely spawns `tsc` and reports real pass/fail
- For an input that should stay freely editable but resync to an external prop only when *that* prop changes (not on every re-render) — e.g. `ListPaginationControls.tsx`'s jump-to-page field — keep it uncontrolled (`defaultValue`, no `value` prop) and push updates imperatively via a `ref` + `useEffect` (`ref.current.value = ...`) keyed on the prop. A `key={prop}`-based remount achieves the same resync but visibly flickers and drops focus/selection, since it tears down and recreates the DOM node instead of mutating it
- `<button>` and `<a>` are both HTML "interactive content" and cannot be nested inside each other in either direction (invalid markup, ambiguous for screen readers) — a nav link that should look like a button needs Tailwind classes applied directly to the `<a>`, not a `<button>` wrapper
- Tailwind v4's bundled Lightning CSS auto-adds vendor prefixes (no `autoprefixer`/manual PostCSS needed) — but that doesn't help hide Firefox's number-input spinner: it needs `-moz-appearance: textfield` specifically, since Firefox treats `none` and `textfield` as different values for that control and `appearance-none`'s generated `-moz-appearance: none` has no effect there
- `reactRefresh.configs.vite`'s `react-refresh/only-export-components` rule blocks a `.tsx` file from exporting both a component and plain functions/types/constants — extract non-component logic to a sibling `.ts` file in the same feature folder (e.g. `features/lots/list-lots-filters.ts` next to `ListLots.tsx`, mirroring the existing `routes.ts` sibling-file pattern); this also makes that logic directly unit-testable without rendering
- The rule above only engages on `.tsx`/`.jsx` files — a barrel file with no JSX of its own (e.g. `components/layout/index.tsx`, `components/ui/index.tsx`) should simply be named `index.ts`, which exempts it from the rule entirely rather than needing a sibling-file split. This also unlocks `export * from './X'` as a barrel style: in a `.tsx` file `export *` still errors (a different message — "This rule can't verify that `export *` only exports components," since the plugin can't see the re-exported names), but in a `.ts` file it's clean
- `Number(value)` coerces whitespace-only strings (`' '`, `'\t'`) to `0`, not `NaN` — a numeric-string parse/filter function must `.trim()` before checking truthiness/parsing, or whitespace silently passes through as a valid `0`
- For filterable list screens, reset pagination (`setPage(1)`) in the same change handler that updates filter state, not a separate `useEffect` — otherwise a filter change can strand the user on a now out-of-range page
- jsdom does not implement real cross-document navigation — assigning `window.location.href` to a different path logs `Not implemented: navigation to another Document` and silently no-ops (the Location's URL is never updated); same-document hash changes work fine since those don't require loading a new document
- Testing a component that both does a hard `window.location.href` redirect *and* mounts a router requires faking `window.location` entirely — its `href` property is non-configurable in jsdom (`Object.defineProperty` on just `href` throws `Cannot redefine property`), so you must replace the whole `location` object via `Object.defineProperty(window, 'location', {...})`, but the replacement must still include `pathname`/`search`/`hash`/`origin`, since react-router's `createBrowserURLImpl`/`createBrowserLocation` (`history.js`) read those directly off `window.location` to match routes — omitting them throws `No window.location.(origin|href) available to create URL` deep in react-router internals. `AuthProvider.test.tsx` is the simpler case (redirects, mounts no router) — `{ href: '' }` alone is enough there
- When stubbing `window.location` across multiple tests in one file (`AuthProvider.test.tsx`), set `configurable: true` on the stub descriptor explicitly — it defaults to `false` when omitted, which permanently locks the property for the rest of the file (including any later restore). Capture `Object.getOwnPropertyDescriptor(window, 'location')` in `beforeEach` before overwriting, and restore it via `Object.defineProperty(window, 'location', originalLocation)` in `afterEach`, so the mock doesn't leak between tests
- `vitest.setup.js` explicitly calls `afterEach(cleanup)` from `@testing-library/react` — required because this project doesn't set vitest's `test.globals: true` (every file imports `test`/`expect`/etc. from `'vitest'` explicitly), so RTL's own auto-cleanup registration (which only self-installs if it finds a bare global `afterEach`) never fires; without this, DOM from one test's `render()` silently leaks into the next test in the same file — invisible as long as every test file only calls `render()` once, which is why it went unnoticed until a multi-render test file exposed it
- `vi.advanceTimersByTime(...)` needs wrapping in `act(...)` (from `@testing-library/react`) whenever the advanced timer is expected to trigger a React state update (e.g. testing a debounce hook) — otherwise an assertion can run before React flushes the resulting re-render
- Hooks are tested via `render`/`rerender` with a tiny local test-only wrapper component, not `renderHook` — per Testing Library's own documented recommendation to exercise a hook through a component rather than in isolation; see `client/src/hooks/index.test.tsx`'s `DebouncedValueProbe` for the pattern
